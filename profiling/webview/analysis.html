1 · Environment & method

Source of truth is profiling/webview/rolling.prof: 7,171,660 function calls in 26.974 s instrumented (2 repeats) from harness.py --path rolling --tickers 300 --years 3 --top 10 --repeat 2 against a stub fetcher — pure engine CPU, no network/parquet I/O. Two flamegraphs corroborate: cProfile (authoritative, call-count-weighted) and py-spy (6,427 samples; noisier — 6.8 % is importlib start-up, used for shape only).

Contention caveat. A concurrent 280-run backtest sweep on this 4-core box inflates every wall-clock number, so all ranking rests on cProfile call counts and cumulative-time share (relative, contention-invariant), not absolute seconds. Tools: cProfile/pstats with targeted print_callers/print_callees cuts, both SVGs, and one isolated perf_counter micro-benchmark.

Prior-work delta (verified in source): July-10 F-01 (share-aware slippage — fills.py:124 now passes shares, ADV/σ gated behind needs_liquidity_inputs) and F-03 (exposure difference-array — metrics.py:118 is now searchsorted + np.add.at + cumsum) have shipped and are gone from the top-40. F-04 (whole-panel Pine evaluation) has not shipped — pine.py still has no cache/context — and is the #1 bottleneck here.

2.1 · Pine evaluation — 32.9 %, largest single cost

pine.py:479 evaluate recursively walks the AST (_eval 7,112 calls → _eval_call 2,656). print_callers confirms two call sites: _precompute_entry_signals (600, once/ticker×2 runs) and the exit-signal cache-miss path in _make_slot_state (428, once per unique ticker — correctly memoized, not per trade). So this is not a per-bar loop — each call is a legitimate whole-history vectorized op over ≤1,200 bars. The cost is per-ticker amplification of pandas' fixed per-call overhead: the real SMA compute (rolling.mean) is only 2.233 s, while _series_from_name's unconditional .astype(float) (3,256 calls → 1.320 s, on already-float64 columns) and _construct_result Series-wrapping (2.951 s) are pure overhead. py-spy corroborates: evaluate is 15.4 % + 7.1 % of samples across two call sites.

2.2 · Generic pandas construction tax

Series.__init__ (17,096 calls, 4.957 s) plus isinstance (1.44 M, 1.582 s), pandas_dtype (39,904), __setattr__ (57,500), sanitize_array (17,950), __finalize__ (32,524), and ~0.8 s of warnings context-manager churn. None of it is arithmetic — it scales with call count, not array size.

2.3 · Fixable bug — eager default pd.DataFrame()

rolling_simulation.py:387: bars = self.bars_by_tv.get(ticker, pd.DataFrame()). dict.get evaluates its default unconditionally, so an empty DataFrame is built and discarded on every candidate popped. print_callees confirms 1,418 DataFrame.__init__ calls, 2.097 s cumtime.

Right-sizing (correction to prior draft). That 7.8 % is cProfile cumtime and inflates high-call-count paths. An isolated benchmark measured a bare pd.DataFrame() at 477 µs (contended), so the true recoverable work is ≈1,418 × 477 µs ≈ 0.68 s (~2–3 % of a real run), not 7.8 %. Still a genuine zero-risk free win — fix: get(ticker) + existing bars is None or bars.empty guard.

2.4 · Per-trade slot setup — _make_slot_state (5.511 s)

Genuinely per-trade (1,418 = 709 trades × 2 runs). print_callees: frame() 2.047 s (all from 428 cache-miss _build_frame_cache builds), exit-signal evaluate 2.043 s, and entry_price 0.756 s — the last still does bars.iloc[entry_idx]["open"] (fills.py:48) instead of the _FrameCache.open_arr array it already holds. The one per-trade path missed when F-03's array cache landed on the exit side.

2.5 · Per-bar exit scan — already vectorized

_check_exit_at_bar (13,680) and _close_slot_at_day (15,098) read frame_cache NumPy arrays with np.searchsorted — ~0.5 s tot for ~29 k calls. This is the F-03 rewrite done; no longer worth optimizing.

This is a latency-bound Python-overhead workload, not a throughput-bound array-math one — and even the small math bucket is fragmented into ~300 tiny per-ticker calls. This single fact decides the GPU question.

3 · GPU verdict — not worth it as architected

Assuming a GPU is available (this VM has none): the profile is latency-bound Python/pandas object overhead inside per-ticker / per-trade / per-bar control-flow-heavy loops — not throughput-bound array math (real float work <10 %). The one existing batch op (candidate matrix, ~227 k cells / single-digit MB) is far below cuDF/RAPIDS break-even. A naive cuDF/cuPy port of the per-ticker Pine loop pays kernel-launch + PCIe overhead thousands of times on ≤1,200-element arrays and would likely be slower (~0.3–0.7×).

Scenarioexpectedreason
Naive GPU port of current per-ticker loop0.3–0.7×launch/dispatch × thousands of tiny calls + PCIe
CPU-side whole-panel Pine rewrite (F-04)1.5–3×collapse ~300× per-ticker call overhead → panel-wide
That batched panel on GPU @ 300-sym/3-yr~flatMB-scale data below cuDF break-even

Precondition to revisit: first do the whole-panel vectorized Pine rewrite (§4.1) — the same change that makes it fast on CPU — then consider GPU only for a workload with real parallel width (much larger universes, or batching many independent backtests: grid search, walk-forward, Monte Carlo, the 280-run sweep) into one numba.cuda/cuDF kernel, never for one backtest's per-bar engine loop. Note: vectorbt (used elsewhere) is already the "batch into one array op" answer, but JITs to CPU via Numba/Rust with no CUDA backend.

4 · CPU-side wins that dominate GPU

4.1 · Batch Pine across the panel — F-04 (biggest)

Rewrite sma/ema/rsi/crossover/crossunder to run on a ~756×300 DataFrame instead of once per ticker in the AST walk. Collapses 2,232 rolling.mean + 3,256 _series_from_name + 7,586 arithmetic dispatches into a handful of panel-wide calls. Pine is 32.9 % of cumtime and mostly overhead, not the rolling.mean math. Normalizing to float once also removes the redundant .astype(float) re-casts. July-10's AST-node memo PoC only got 2–10 % because it didn't cut per-ticker call shape; this cuts call count by the ticker factor. Plausibly 1.5–3× end-to-end.

4.2 · Route entry_price through the frame cache

fills.py:37–64 still does bars.iloc[entry_idx]["open"] though a _FrameCache with open_arr/close_arr/low_arr is already in scope. ~0.756 s / 1,418 calls; mechanical, low-risk.

4.3 · Fix the eager pd.DataFrame() default (§2.3)

rolling_simulation.py:387 → get(ticker). ~0.7 s recoverable, one line, zero behavior change.

4.4 · F-01 / F-03 already landed — no action

Share-aware slippage and the exposure difference-array are verified fixed and absent from the top-40. The diffuse isinstance/pandas_dtype/construction tax (§2.2) shrinks proportionally once 4.1 cuts call counts — re-profile after.

5 · Bottom line

  • Profile is dominated by Python/pandas object & dispatch overhead; real vectorizable float math is only ~2–10 %. Latency-bound, not throughput-bound.
  • Pine evaluation is #1 at 32.9 % cumtime — overwhelmingly per-ticker call overhead, not the SMA it computes.
  • GPU offload is not worth it for this engine as architected — sequential per-bar/per-trade state machines or per-ticker calls on arrays too small to clear PCIe/launch cost; a naive port would likely be slower. The precondition for GPU is the whole-panel rewrite, which is itself the CPU win.
  • Highest-ROI CPU fix: batch Pine across the panel (F-04, §4.1), ~1.5–3×. Then two cheap wins: frame-cache the entry fill (~0.76 s) and drop the eager pd.DataFrame() (~0.7 s).
  • Corrections to prior draft: its "7.8 % of runtime" for the DataFrame bug is cProfile cumtime and over-states recoverable wall-clock (real ≈0.7 s / ~2–3 %); it mislabeled _construct_result cumtime as 2.485 s (own cumtime is 2.951 s). F-01/F-03-shipped and F-04-not-shipped are confirmed correct.
